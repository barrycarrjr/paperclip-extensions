# Amazon Seller Tools

Generic, company-scoped Amazon Selling Partner API (SP-API) reads for a seller's own private-developer account, plus generation of a small allowlist of read reports. One configured connection represents one seller. There is no third-party OAuth onboarding, operator-login sharing, core change, or Amazon Ads authentication.

> **Install + setup walkthrough** lives in-app: open the plugin's settings page in Paperclip and follow the **Setup** tab. This README is an overview of capabilities and a reference for tool/event shapes.

## Recent changes

- **v0.3.0** - Consolidates Listing Watch with the company-scoped transport, credential checks, projected outputs, opaque cursors and governed report operation. Adds listing search, offers, company-owned change history and both scheduled checks. Preserves the exact 0.2.0 migration and stored rows. Legacy configuration remains accepted; unowned historical rows stay private and a new baseline starts. The deployed 0.2.0 upgrade has the same nine capabilities and activates immediately; correct configuration before upgrading.
- **v0.2.0** - Earlier Listing Watch implementation with account-key snapshots. Its historical migration and data remain retained. Its request helpers are now disabled reference code; every executable call uses the shared service.
- **v0.1.0** - Initial seller finance, balances, settlement reports, FBA and merchant inventory, Orders 2026-01-01, Catalog Items, seller Listings Items, A+ Content, and inspection of existing Notifications subscriptions/destinations. Includes company isolation, encrypted credential references, bounded downloads, whole-record paging with cursors and offsets, per-operation token-bucket pacing from Amazon's published burst and rate, explicit `writes` declarations (only `amazon_request_report` is a write), host failure codes, per-tool execution timeouts, output projection, activity logging, and synthetic protocol tests. Ads and notification ingestion are excluded.

A+ monitoring records document name/status and hashes complete selected text plus supported image upload identity, alternative text and crop dimensions before display cuts. A module with more than 50 text items or more than 32 KiB of display strings can still be monitored; public content tools keep their 50-text limit and truncated flag. Hash bounds remain 256 KiB of selected UTF-8 text, 2,000 visited nodes, 24 levels and 100 children per declared array, with at most 100 modules and ten module pages per document; exceeding them fails the check without replacing its earlier snapshot. Image identity is never returned in clear. Comparison deliberately excludes videos, video thumbnails, standard comparison-table ASINs, highlight flags, decorator types/content (only declared structure presence can affect the hash), image position/color options, raw URLs and unknown fields. Full 0.2.0 raw-module comparison parity is not claimed.

## Upgrade from 0.2.0

1. Correct configuration before installing 0.3.0. The deployed 0.2.0 has the same nine capabilities, so the host does not pause this upgrade for approval: stored configuration activates immediately. Disable the old watch before upgrading if corrections cannot be completed first. New installations and upgrades from 0.1.0 can require capability approval. Keep `amazon-tools`, database namespace slug `amazon` and the existing installation identity. The archive includes the original `0001_listing_watch.sql` unchanged plus forward migration `0002_company_watch.sql`. Do not remove the plugin's database or replace the historical migration.
2. Every legacy account now requires `sellerId`, including finance-only accounts where 0.2.0 allowed it to be omitted. Obtain the actual seller ID before upgrading; it is never guessed. Existing `name`, `defaultAccount`, lowercase `na`/`eu`/`fe`, `sellerId`, `lwaClientIdRef`, `lwaClientSecretRef`, `refreshTokenRef` and explicit `listingWatch` values remain accepted. Each legacy reference must be a current secret owned by the calling company. Alternatively use the combined `credentialsRef` JSON described below. Never combine the two credential modes in one account: partial or mixed credentials fail configuration validation. Saving never rewrites the stored configuration or enables an absent/false watch switch.
3. Replace `"*"` and invalid company lists with explicit company IDs. Empty lists deny access. Keys must be unique lowercase letters/digits/hyphens, start with a letter/digit and contain at most 40 characters. Rename uppercase or underscore keys and update callers and `defaultAccount` before upgrading; a stale default is invalid. Names are at most 120 characters without control characters. Duplicate company/marketplace IDs, invalid credential references, unknown fields, mixed credential modes or one invalid entry reject the entire configuration, including otherwise valid accounts for other companies. Limits are 20 accounts, 20 allowed companies per account and ten marketplaces per account. Separate company-owned credentials are needed for separate companies; jobs never resolve an unscoped secret.
4. Historical 0.2.0 rows contain no company identity. They remain unchanged in the three original tables, but tools never expose them or infer ownership from an account key, current allowlist or seller label. New company-owned baselines and history use separate tables. Changes are reported after a complete new baseline. Changing the company, credential references, seller identity, region or marketplace configuration selects a separate history scope and starts another baseline; old scopes are retained, not transferred. Rotating material under the same references for the same seller keeps that scope, while invalidating token/cursor caches.
5. Update existing callers using the compatibility rules below. The settings **Test Configuration** action now performs local validation only; use `amazon_test_connection` in an allowed company for the actual fixed-path connectivity read. It is deliberately separate because settings validation has no calling-company context. Health remains worker readiness. A connection test or watch can never generate a report.

An omitted account uses `defaultAccount` when configured, subject to current company access; otherwise it requires exactly one allowed account. Multiple marketplaces require `marketplaceId`, including for legacy accounts. No first-marketplace guess is made.

## Listing Watch

`listing_watch_status` runs at `17 */6 * * *` UTC. `listing_watch_content` runs at `43 7 * * *` UTC. Only accounts explicitly set to `listingWatch: true` are visited, under each explicit allowed company whose secrets resolve for that company. A failed company is never replaced with another owner. Jobs use the same fixed reads, authentication revalidation, pacing, download bounds and projections as tools. They cannot call report generation.

Each marketplace/kind begins with a baseline and no listing-change alerts. Later checks record one row per changed field, including additions/removals, status, issues, our price, Buy Box, offer count, other seller IDs, submitted versus live content, images, category and A+. These are comparisons of API evidence; they do not identify who changed content or guarantee a rendered retail page. Our own seller ID is omitted from offers; `MyOffer` identifies our offer. Failed optional offers/A+ preserve prior values and record explicit unavailable coverage counts. Successfully read fields can still save and record changes when other sources are unavailable, but that run has `ok: false`, `complete: false`, `degraded: true`. A genuinely unknown or newly introduced stored field establishes its own baseline on first observation.

Selected watch text over 1,000 characters is represented by a bounded prefix and SHA-256 fingerprint of the full selected, scrubbed text. Changes beyond the prefix are detected without widening public tool output. Reflected credentials, invalid text normalization, oversized structures and missing required pages still make a check incomplete. Availability belongs to the source: an eligible marketplace summary or a selected attributes object in a successful response makes its omitted fields observed null/empty lists. Removed descriptions, search terms, bullets, images and prices, and later additions to empty fields, therefore record changes. Ordinary absent search terms, image or live description do not degrade a run. No eligible summary, no ASIN for live reads, a missing attributes object or failed optional read is genuine unavailability: keep prior values or omit never-observed fields, with source counts. Omitted issue arrays are conservatively unknown; no provider guarantee about their omission is claimed.

Internal content reads request only submitted listing attributes and catalog attributes/images/product types/summaries, and project only fields the snapshots consume. Unused identifiers, variation relationships and unrelated attributes cannot exhaust a watch projection. Selected listing/catalog evidence still fails on any partial used value under the per-record 1,400-node, 16-level, 100-item-array and 32 KiB display-string bounds; long individual strings retain their full-text hash.

Offers, catalog and A+ evidence are fetched once per distinct ASIN within one authorized marketplace check; submitted listing attributes remain separate per SKU. A+ documents shared by ASINs are fetched once per content reference. The check-local cache has an aggregate 4 MiB bound, is never reused across checks/companies/credential scopes, and rechecks current ownership before cached evidence is consumed. Every outbound attempt still checks ownership after waiting, and snapshots check before commit and before returning. Combined `credentialsRef` costs one secret lookup per ownership check; legacy references cost three, under the same unchanged background budget.

The total job work budget is 240 seconds within the host's default five-minute job timeout. Enumeration is bounded by 100 whole-record pages and at most 2,000 listings, ten A+ documents per ASIN, 100 projected modules per document and 4 MiB each for its new snapshot and change batch. These are hard bounds, not a catalog-size promise. The snapshot and change byte limits are checked during accumulation as well as before commit. A catalog exceeding these bounds, structurally truncated record, incomplete page, repeated provider page, deadline or failed required read fails the check without replacing its completed snapshot or inferring removals. Partial marketplace scans are not resumed across schedules. The worker rotates the first company/marketplace target between jobs so later targets can make progress; that scheduling position is memory-only and resets on worker restart. 41- and 80-listing synthetic checks complete under the ordinary modeled quota and deadline; this is not a live capacity guarantee. Catalogs that cannot finish need an operator to reduce monitored scope where possible outside this plugin or disable watch pending future resumable scanning. No listing filter/resume feature is provided by this release. Large catalogs can therefore remain incomplete; check the recorded outcome rather than treating a quiet change log as healthy. The host currently awaits each dispatched plugin job inside its scheduler tick, so a long check can delay other due plugin jobs by up to this budget. Custom host job timeouts shorter than 240 seconds are unsupported because the SDK does not supply the actual deadline.

A local deadline, pacing refusal or secret-lookup budget that prevents remaining coverage aborts the check and retains its previous snapshot and history. A recorded failure has `ok: false`, `complete: false` and exact not-attempted counts when enumeration identified the targets. Optional provider failures can save known observations while preserving unavailable fields, but never return complete coverage. The scheduled job fails if any target is incomplete. `coverage.offers`, `.catalog` and `.aplus` report distinct-ASIN `required`, `read`, `providerFailures`, `budgetFailures` (started but reached the deadline), `notAttemptedBudget` and affected `unavailableListings` counts; `coverage.submitted` reports the same counts per SKU for content reads; `coverage.sources` counts listings with genuinely unavailable sources. `enumerationComplete` states only whether all listings were enumerated. It never substitutes for whole-check `complete`.

Snapshots and their history append commit in one namespace SQL statement, guarded by a saved revision. Concurrent stale checks fail instead of overwriting a newer snapshot or duplicating changes. A lost database reply can have committed; the next check compares against committed state and does not repeat those changes. A whole job is not one transaction across all companies/marketplaces: earlier complete marketplaces can save before a later one fails. Host RPCs cannot be cancelled through the SDK, so a late database reply can leave an uncertain committed outcome, visible in subsequent checks.

`amazon_list_listing_changes` accepts `account`, optional `since` (defaults to seven days ago), `marketplaceId`, `sku`, `asin`, `field`, `limit` (1 to 100) and opaque `cursor`. It returns `changes`, `health`, `recentChecks`, `nextCursor`, `through` and `truncated`. Each change has `id`, `detected_at`, `marketplace_id`, `sku`, `asin`, `kind`, `field`, `before` and `after`. `health` contains every configured marketplace and both status/content kinds, with its latest run or `latest: null` when missing. Each latest run exposes `complete`, `enumerationComplete`, `degraded`, structured `coverage` and a fixed `error` code when available. Earlier plain-note rows have `complete: null` and `coverage: null`; they provide no full-coverage proof. If timestamps tie exactly, an incomplete receipt is preferred conservatively. `recentChecks` contains the latest recorded run per marketplace/kind (up to 20), rather than a global last-four list. Inspect health even on a quiet change log. The complete history response, including all health metadata, is capped at 96 KiB; changes use the remaining space and continue as whole rows. Structured notes are returned as short labels with separate coverage counts. Results are oldest first. Repeat the same filters with the returned cursor, including through empty pages, until `nextCursor` is null. The query's start/end window is fixed for the chain. This is bounded pagination over append-only records, not a database snapshot isolation guarantee. Deduplicate by change `id`, persist processed IDs with the review log, and advance `through` only after all pages and required authorized actions finish. Begin the next review ten minutes before the last completed `through`, retaining IDs for at least that overlap. This recovers ordinarily delayed commits, not arbitrarily late host/database work or clock jumps. Periodically reread the full seven-day review interval with retained IDs to recover longer delays; beyond that interval an operator must choose a wider explicit `since`. No finite overlap guarantees visibility of indefinitely delayed commits. Current company/config/secret checks apply even when reading stored history. Original unowned tables are never queried by these tools.

The companion agent, bundle, skill and review/digest routines are templates only. Importing this package does not activate them, assign an agent, configure Slack or authorize a channel post. Their instructions inspect structured coverage, record operational limitations and deduplicate new or worsened operational notices separately from urgent listing changes. A quiet review posts nothing.

## Legacy tool compatibility

- Matching aliases are explicit: list `maxResults` and listing/report `pageSize` map to `limit`; a one-element `marketplaceIds` maps to `marketplaceId`; a one-element `reportTypes` maps to `reportType`; inventory `channel: "fba"`/`"merchant"` maps to explicit `fulfillment`, with one-element `skus` mapped to `sku`. Conflicting aliases fail. Multiple marketplaces/SKUs/report types require separate calls. Inventory needs `fulfillment` or `channel`; the former implicit FBA default is no longer used.
- `amazon_get_order` accepts legacy `includeItems: true`, matching the safe item summaries it always returns. `false` returns actionable `ECOMPAT`; omit it or use true. `amazon_get_report` accepts legacy row limits 101 to 500 by clamping to 100 whole rows, preserving all later rows through the returned offsets.
- Raw `nextToken` is refused with `ECOMPAT`: restart the query and use its company/query-bound `nextCursor`. Omitted order start dates, the old order-status/channel filters, financial `maxPerType`, settlement `startedAfter`/`startedBefore`, report `processingStatuses` and caller `reportOptions` are not silently translated. Supply the documented current date/filter arguments; fixed report options and projections remain enforced. Current schemas reject other unknown inputs.
- `amazon_list_settlements` now lists V2 settlement **report metadata**, not legacy financial event groups. `amazon_get_settlement` requires `reportId`; an old `settlementId` is refused with an actionable `ECOMPAT` message. To research a financial event group, use `amazon_list_financial_events` with explicit dates, `relatedIdentifierName: "FINANCIAL_EVENT_GROUP_ID"` and that group ID as `relatedIdentifierValue`. An event group ID is never sent as a report ID.
- `amazon_get_aplus_content` accepts exactly one of `contentReferenceKey` or legacy `asin`. ASIN mode returns `documents` for at most five complete documents and refuses larger/paged aggregates with `ECOMPAT`. For full results, use `amazon_list_aplus_publish_records` with cursors and then key-based module offsets. Outputs use the safe nested service projections, not the old flattened listing/catalog/offer shapes. Use `listings`, `listing`, `item` and `offers` wrappers as declared; the watch comparison helpers consume those same projections.
- Change reads now cap `limit` at 100 and use cursors rather than moving `since` forward mid-page. Permission, host, response and unknown/accepted report failure classifications are preserved. `amazon_request_report` remains the only `writes: true` tool and is never retried automatically.

## Install and configure

1. Build from this repository using Node 22 or newer. From `plugins/amazon-tools`, run `pnpm install --frozen-lockfile` and `pnpm build`. The build uses the existing `vendor/sdk/*.tgz` packages; do not repack the SDK. Install the resulting plugin through Paperclip's ordinary Plugin Manager or local-plugin installer. Release packaging discovers this folder automatically.
2. Register a private SP-API application for your own seller account, request the roles below, then self-authorize it. Amazon eligibility and approval still apply. [Amazon's connection instructions](https://developer-docs.amazon/sp-api/docs/connecting-to-the-selling-partner-api) describe self-authorization and Login with Amazon (LWA) token exchange. LWA is Amazon's authorization service. SP-API does not require AWS IAM keys or Signature Version 4 signing.
3. On the **Secrets** page of each company that will use the connection, create a secret, for example named `AMAZON_SP_API_CREDENTIALS`. Its value must be JSON with exactly these four string fields:

   ```json
   {"clientId":"example-client-not-real","clientSecret":"example-secret-not-real","refreshToken":"example-refresh-not-real","sellerId":"SELLEREXAMPLE"}
   ```

   The plugin settings form cannot create secrets. Its **Encrypted LWA credentials JSON** field picks one of the company's existing secrets, or takes a pasted secret ID. Configuration retains only `credentialsRef`. The worker resolves that reference with the calling company through `ctx.secrets.resolve(ref, companyId)`. There is no plugin credential input/read-back action, raw-credential config field, or credential output tool. Never pass credential values as tool arguments.
4. In Configuration, add a unique connection key, pick the secret, choose `NA`, `EU` or `FE`, and add marketplace IDs served by that region. Select explicit allowed company IDs. Missing, empty, malformed, duplicate or wildcard company lists deny access. The selected secret must belong to the calling company. For multiple companies, use separate connection entries and company-owned secrets; a reference belonging to another company will fail resolution.
5. Save, then call `amazon_test_connection` from an allowed company's agent. Include `account` if that company has multiple configured connections, and `marketplaceId` if the connection has several marketplaces. This reads one listing and confirms that authorization path. It does not prove optional roles. Settings config validation checks structure only; worker health is not a live Amazon connection test.

The host's secret service stores the encrypted value. The SDK's `ctx.secrets.store` is available for plugin-owned generated material, but this plugin does not invent a second credential-entry UI or store credentials in plugin state. No saved secret values are returned by this plugin.

## Report generation is declared as a write

`amazon_request_report` is the only tool that changes anything outside Paperclip: it asks Amazon to create a report. Following Paperclip's plugin spec (sections 11.1 and 11.7), it is declared `writes: true` with no `actionType`, because none of the host's action categories fits. Every other tool is declared `writes: false`, so the host never guesses from a tool's name. What that means in practice:

- **Approval.** For an agent run, the host treats a write without an action category as "ask first", so each agent call is queued for a person to approve and runs once approved. The host's per-category action settings do not apply to it. Clippy chat calls, made by a person, are not held by this policy.
- **Repeat protection.** The host claims each call before running it. A repeat of the same call in the same run (or with the same scoped idempotency key) replays the first result instead of creating a second report. The current host does not check a settled result's expiry when replaying it, so this is not a reliable 30-minute retry window.
- **What the plugin returns.** Before the report POST is sent (invalid input, company or configuration denial, credential or sign-in failure, a rate wait that is too long, an unopened connection, or the deadline passing before sending), no report can have been created. A 4xx refusal, including 429, did reach Amazon but is assumed to mean no report was created. In both cases the failure is raised as an error so the host releases its claim and an identical retry may run. When the report POST may have taken effect, the failure is returned as a settled result: `EREPORT_UNKNOWN` (network error, 5xx, deadline or invalid reply after sending) or `EREPORT_DISPATCHED` (Amazon accepted it, but the connection's configuration or credentials changed before the result returned, so the report ID is withheld). Neither should be repeated blindly; call `amazon_list_reports` first.
- **Duplicate-report limits.** If Amazon created a report but still answered 4xx, releasing the claim would let a retry create a second read report. If the worker crashes or is stopped during the POST (upgrade, disable, uninstall or instance shutdown), the host sees an RPC error and releases its claim, with the same risk. Repeat protection cannot guarantee exactly one report at the external provider.
- Report creation is never retried automatically, including after a 429.

## Reports, settlements and payouts

The report allowlist is deliberately small:

- `GET_V2_SETTLEMENT_REPORT_DATA_FLAT_FILE_V2`: Amazon-generated TSV, discover/download only. Deposit dates and settlement totals provide payout reconciliation evidence. There is no fictitious list-settlements API. [Amazon's settlement report rules](https://developer-docs.amazon/sp-api/docs/report-type-values-settlement).
- `GET_FLAT_FILE_OPEN_LISTINGS_DATA`: requested merchant listing inventory/price summary. No buyer data. [Inventory report definition](https://developer-docs.amazon/sp-api/docs/report-type-values-inventory).
- `GET_FBA_MYI_UNSUPPRESSED_INVENTORY_DATA`: requested FBA inventory summary. [FBA report definitions](https://developer-docs.amazon/sp-api/docs/report-type-values-fba).
- `GET_SALES_AND_TRAFFIC_REPORT`: requested aggregate sales/traffic JSON. Requires `dataStartTime` within two years; the plugin limits the date range to at most 30 days, ending over two minutes ago. If `dataEndTime` is omitted, it uses the earlier of now minus three minutes and start plus 30 days, so approval delays do not make the window exceed the limit. Supply an explicit end for an exact window. Both inventory report types refuse start/end dates. The 30-day cap is the plugin's choice: [Amazon](https://developer-docs.amazon/sp-api/docs/report-type-values-analytics) recommends 7 to 30 days to reduce processing time and only requires the start to be within two years. The plugin fixes granularity to DAY and SKU. No arbitrary report options.

`get_report` first verifies the report type and marketplace scope, then obtains its document metadata internally. Only known columns or aggregate JSON fields are returned. No raw reports, pre-signed URLs, unrestricted text, order reports, tax reports or buyer details are exposed. TSV files with unknown/localized headers, duplicate headers, multiline values or rows with the wrong number of columns fail closed rather than guessing column positions. Quote characters inside a cell, such as an inch mark in a product name, are ordinary data. Decimal commas are preserved as strings.

Report documents are decoded with the charset their download declares in `Content-Type`, as in [Amazon's retrieve-a-report sample](https://developer-docs.amazon/sp-api/docs/retrieve-a-report). Supported labels are UTF-8, windows-1252 (including `Cp1252`) and Shift_JIS (including `windows-31j`); windows-1252 is decoded from the WHATWG table because Node's own decoder maps 0x80 to 0x9F as control characters. Any other label, or more than one charset parameter, fails with `EDOWNLOAD`. A download with no charset is decoded as strict UTF-8 only, so a non-UTF-8 document without a label fails rather than being guessed. Which charsets Amazon actually declares for each marketplace has not been verified against a live account.

Finances uses current transactions, not a legacy events endpoint. Date windows are limited to 180 days and must end over two minutes ago; results may lag 48 hours. `ORDER_ID` and `FINANCIAL_EVENT_GROUP_ID` are the supported identifier filters. The response may contain settlement/disbursement identifiers for reconciliation. By default, finance reads the authorized seller account across marketplaces, because Amazon explicitly warns that supplying `marketplaceId` excludes US merchant-fulfilled transactions. Specify a configured marketplace only when that restriction is intended. [Current transaction contract](https://developer-docs.amazon/sp-api/reference/listtransactions).

## Listing Watch and Notifications boundaries

For comparison, read the catalog ASIN with `amazon_get_catalog_item` and the seller SKU with `amazon_get_listing`. Catalog data represents Amazon's catalog view; Listings Items attributes represent the seller's latest submitted values, while fulfillment availability is live. These reads do not identify the author of an override or reproduce every rendered retail detail-page element. Selected title, bullets, description, brand and image fields are supported; arbitrary product-type contact/compliance attributes are excluded. [Amazon's explanation of submitted versus live listing data](https://developer-docs.amazon/sp-api/docs/listings-items-api).

A+ text comes from `TextComponent.value`, `PlainTextItem.value` and comparison product titles (`StandardComparisonProductBlock.title`), so standard comparison tables return their product titles, metric values and row labels. A+ list continuations send `pageToken` as the only query parameter, following the explicit pagination rule in the [searchContentDocuments](https://developer-docs.amazon/sp-api/reference/searchcontentdocuments) and [searchContentPublishRecords](https://developer-docs.amazon/sp-api/reference/searchcontentpublishrecords) references. The same references also mark `marketplaceId` as required, which contradicts that rule; live behavior has not been verified.

The four notification types above can be inspected only after an operator provisions destinations/subscriptions for the same application and seller through an approved external process. `ANY_OFFER_CHANGED` commonly uses SQS; the listing status/issues and branded-content events support EventBridge workflows. See [Amazon's EventBridge setup](https://developer-docs.amazon/sp-api/lang-en_EN/docs/set-up-notifications-with-amazon-eventbridge) and [Notifications guide](https://developer-docs.amazon/sp-api/docs/notifications-api). This plugin creates no AWS resources or subscriptions, makes no SQS receive/delete calls, and has no Notifications event consumer, webhook or push alerts. The separate scheduled Listing Watch checks described above poll listing evidence. Application destination inspection is app-wide, not a list of this seller's received events.

## Paging and continuation

- A response holds whole records only: at most `limit` records where the tool has `limit` (1 to 100, default 25), and at most 72 KiB and 1,400 projected nodes of records. A record that does not fit is never dropped; it stays reachable.
- List tools return `nextCursor` while anything remains. For Amazon API lists, a cursor first serves the records of Amazon's page that were already fetched but not yet returned, then asks Amazon for the next page with the original filters (report and A+ lists send only Amazon's page token, as Amazon requires). Reuse the same arguments plus the cursor; a cursor can be retried, returns the same page each time, and is not used up by a failed call. Finance and Orders fix omitted end dates on the first call; later continuations use those validated absolute dates. Orders requires exactly one creation/update start and only its matching end, with a maximum 730-day window. `nextCursor: null` means the end. Empty pages with a cursor still require continuation.
- Cursors are random, memory-only handles tied to the operation, exact arguments, company, connection and current credentials. Each newly issued cursor expires after 15 minutes, on worker restart or configuration change, or when evicted (at most 500 cursors and 24 MiB of cached records per worker, oldest first). Continuing with fresh cursors keeps a chain alive beyond 15 minutes; reusing an old cursor does not extend that cursor's lifetime. An expired, evicted or foreign cursor returns `ECURSOR`; repeat the query without a cursor. Provider tokens have separate hard lifetimes only where Amazon documents one: [FBA inventory](https://github.com/amzn/selling-partner-api-models/blob/main/models/fba-inventory-api-model/fbaInventory.json) 30 seconds (the plugin uses 25 seconds for a safety margin), and [Orders](https://github.com/amzn/selling-partner-api-models/blob/main/models/orders-api-model/orders_2026-01-01.json) 24 hours. A cursor that needs the next provider page after that returns `EPAGE_EXPIRED` without sending the expired token; already fetched records remain readable within the local cursor lifetime. Other tokens have no invented hard expiry; Amazon can still reject an expired token. For a full FBA snapshot use the FBA inventory report, or narrow with `sku`.
- Cached records are the projected, secret-scrubbed output, never raw provider data, download URLs or buyer fields.
- Downloaded reports use row offsets: `nextOffset` counts the rows actually returned, and `null` means the end. For the sales and traffic report, `salesAndTrafficByDate` and `salesAndTrafficByAsin` page independently. With no offsets, both arrays start at 0; afterwards pass `dateOffset` and/or `asinOffset` for the arrays you still need, each from its `nextDateOffset` or `nextAsinOffset`. Naming only one array reads only that array. `offset` is accepted as a shorthand that starts both arrays at the same position and cannot be combined with the specific offsets.
- The projected rows of a DONE report are kept in memory for 15 minutes (at most 8 reports and 16 MiB per worker), bound to the company, connection, current credentials, tool and report ID, so later offsets do not download the document again. Configuration rechecks still run before every result. Rows of a very large document may not be cached; those pages download the document again.
- `amazon_get_aplus_content` returns whole modules per call and continues with `moduleOffset` and `nextModuleOffset`.
- `truncated: true` means a returned record had fields trimmed: a nested list over 100 entries, a string over 1,500 UTF-16 code units, more than 32 KiB of text in one record, or one record too large for a response on its own (it is projected again with fewer nodes). Text cuts preserve complete surrogate pairs (including emoji); NUL characters are removed and already unpaired surrogates are replaced with U+FFFD so projected text can be stored as PostgreSQL JSON. Text normalization also sets `truncated`. A+ returns up to 50 text items per module and reads at most 100 modules.

## Bounds, retries and privacy

- A worker-wide rolling lookup budget reserves at most 600 watch secret resolutions and 900 total resolutions per 60 seconds, below the host backstop of 1,200. Watch leaves at least 300 plugin lookup slots for interactive reads and another 300 below the host limit. Reservations count lookups, never cache ownership. Work waits within its deadline or fails honestly. The budget remains across configuration changes and includes all companies/marketplaces. Separate worker instances and other host-side users are outside this worker-local budget. Fixed failure health records use only the previously authorized scope and error code even if a later lookup is refused; initial authorization failures emit fixed company activity without reading private history.
- Company checks precede secret resolution and networking. The worker reloads config and rechecks current company-owned secrets before every network attempt after waits, before cached watch evidence/page reuse, before and after snapshot commit, and before every external tool/history result, including memory results. Internal watch reads omit a redundant end-of-read check because commit and external-result checks remain. Credential/config changes invalidate authorization reuse. Tokens are cached only in memory, separated by company/config/credential digest and authorization grant; references are resolved afresh on every call. Config changes/shutdown clear tokens, cursors, cached report rows and pacing state.
- Every invoked tool attempts a fixed-metadata activity start and outcome entry, including failures. Entries contain operation, outcome, bounded result count and truncation flag, never arguments, credentials, seller details, provider response bodies or report URLs. An unavailable start audit prevents network access. A failed outcome entry is logged as a worker warning and does not turn a completed call into a failure. No external telemetry is used.
- Fixed LWA and regional API hosts only. No arbitrary URL, method, endpoint or authentication passthrough. Report downloads allow HTTPS S3 bucket/CloudFront host shapes only, verify and pin public IPv4 DNS addresses, validate TLS, reject redirects/embedded credentials/extra ports, and receive no Amazon access-token header. IPv6-only networks and other download host shapes are unsupported and fail closed.
- The transport runs inside the worker using Node HTTPS because the current SDK HTTP bridge drops redirect/abort controls and buffers response text. Each request has an 8 MiB byte cap and ends at 20 seconds or the call's total deadline, whichever is first; gzip expansion is also capped at 8 MiB. No raw document is saved to disk. [Amazon's report retrieval workflow](https://developer-docs.amazon/sp-api/docs/retrieve-a-report).
- Each tool declares `executionTimeoutMs`: 120 seconds for `amazon_get_report` and `amazon_get_settlement`, 70 seconds for the rest. The worker ends its own work, including host lookups and rate waits, 20 seconds before that, so the host never gives up on a call that is still running. A read that reaches the deadline returns `EDEADLINE`; a report request interrupted after sending returns `EREPORT_UNKNOWN`.
- Pacing is a token bucket per seller, application and operation, seeded with Amazon's published burst and refilled at the published rate (for example `searchOrders` 20 calls then 0.0056 per second, `getReportDocument` 15 then 0.0167 per second). `x-amzn-RateLimit-Limit` replaces the rate for that seller, application and operation only; zero, negative or malformed values are ignored. GETs retry only HTTP 429, at most three attempts, waiting for `Retry-After` or an exponential backoff. A required wait over ten seconds, or one that would cross the deadline, returns `ERATE` with seconds to wait instead of sleeping. Independent worker processes still share Amazon's upstream limits; pacing is local to one worker.
- Failures carry Paperclip's failure codes, so agents get the right next step: `invalid_input` (bad arguments, `ECURSOR`, `EPAGE_EXPIRED`), `not_authorized` (company, configuration or report scope), `needs_reconnect` (credentials or Amazon authorization), `unavailable` (network, `ERATE` with `retryAfterMs`, activity log), `timeout` (`EDEADLINE`), `not_found` (HTTP 404) and `failed` (everything else, including `EREPORT_UNKNOWN` and `EREPORT_DISPATCHED`).
- Amazon sign-in network failures, 429 and 5xx are transient failures, not a request to reconnect. A 429 carries a sanitized `Retry-After` hint; only HTTP 400/401 or a malformed token grant means `EAUTH`. Host configuration/secret lookup trouble returns sanitized `EHOST` (`unavailable`); missing/foreign secret references and malformed credentials remain `ECREDENTIALS`, while company/configuration denial stays permanent. Oversized plain or gzip responses keep `ERESPONSE` (`failed`, not retryable), rather than inviting another download.

## Deliberately excluded data

These fields are left out on purpose, to keep free-form provider text, payment details and buyer data out of agent context. Adding any of them is a scope decision, not a bug fix:

- Listing issue `message` text (codes, severity, attribute names and categories are returned).
- Transaction `description` and every transaction `contexts` entry, including product, deferral and payment/bank contexts (so deferral reasons and maturity dates are not returned).
- Order buyer, recipient, tax, payment, gift and customization data, even if Amazon returns it.
- The configured seller ID and every credential value are replaced by `[redacted]` wherever they appear in returned data, even inside other values, such as a SKU that contains the seller ID. Selected strings are scrubbed before normalization and text cuts, then again after normalization and projection; unselected raw objects are never recursively copied for redaction.

Sellers without A+ eligibility will see every content check incomplete and every content job failed. Without the Pricing role, every status check is incomplete and every status job fails. Any ASIN-less listing makes both checks incomplete and both jobs fail on every run until resolved.

Before enabling Listing Watch, an operator must run amazon_list_listings from an allowed company for a known issue-free listing in each marketplace and inspect the returned issues key. It must be present as an empty array. If it is omitted, leave the watch disabled and report the response shape for review; the current conservative handling marks the status check incomplete. This live acceptance check has not been run.

An unchanged limitation: a provider 429 with Retry-After above ten seconds blocks its operation bucket; a later local refusal can be counted as budget, aborting the check without saving other evidence.

## Verification

From `plugins/amazon-tools`:

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
pnpm test:runtime
```

The tests use synthetic credentials and data only. `src/coverage.test.ts` covers 120/140-ASIN incomplete status checks, 40/80/100/140-ASIN content capacity with counted lookups, absent-key additions/removals, ordinary empty values, shared-ASIN reads and current-ownership checks. `src/amazon.test.ts`, `src/continuation.test.ts`, `src/limits.test.ts` and `src/worker.test.ts` retain the finance, authorization, paging, report, network and worker regressions. `src/listings.test.ts` adapts the earlier listing/diff/watch cases without replacing global transports or clocks; `src/repair.test.ts` adds lookup-budget headroom and slow-host timing, long-text fingerprints, unknown/empty fields, 41/80-listing capacity, health/template and compatibility regressions; `src/upgrade.test.ts` covers configuration, migration checksum, retained old rows, ownership, revocation, incomplete pages, failed commits, lost replies and concurrent jobs. Runtime tests copy only built artifacts into retained isolated scratch installations under the checkout's ignored `.smoke-tests/`, validate the manifest, launch the actual bundled worker over JSON-RPC, and route its real HTTP construction to loopback fixtures. The union runtime case runs both jobs against a migrated PGlite namespace through serialized host-like SQL parameters/results. Setting `AMAZON_HOST_SQL_VALIDATORS` to an isolated bundle of the host's actual exported validators additionally validates every fixture runtime statement and migration. No root test setup or real database is used. The transport adapter is outside `dist/` and cannot change production endpoints.

Runtime cases also cover sign-in failure classification and 9 MiB plain/API responses plus oversized gzip expansion through the real transport. To include the isolated PostgreSQL JSON roundtrip, set `AMAZON_TEST_PGLITE_MODULE` to an already installed PGlite module file before `pnpm test:runtime`. This optional test uses an in-memory database, rejects the original NUL/unpaired-surrogate examples, then roundtrips the worker's projected output; it adds no runtime dependency.

Live seller acceptance remains an operator step: approve roles, create the secret, pick it in the settings form, run the connection test, then call the relevant tools with real report/order/ASIN/SKU IDs. Live credentials, eligibility, account-specific schemas, Amazon's real page sizes and charsets, and secret UI masking have not been verified against a running Paperclip instance or a real seller account. Amazon Ads remains phase 2 with separate authentication.
