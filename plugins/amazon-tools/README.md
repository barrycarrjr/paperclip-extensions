# Amazon Seller Tools

Generic, company-scoped Amazon Selling Partner API (SP-API) reads for a seller's own private-developer account, plus generation of a small allowlist of read reports. One configured connection represents one seller. There is no third-party OAuth onboarding, operator-login sharing, core change, or Amazon Ads authentication.

> **Install + setup walkthrough** lives in-app: open the plugin's settings page in Paperclip and follow the **Setup** tab. This README is an overview of capabilities and a reference for tool/event shapes.

## Recent changes

- **v0.1.0** - Initial seller finance, balances, settlement reports, FBA and merchant inventory, Orders 2026-01-01, Catalog Items, seller Listings Items, A+ Content, and inspection of existing Notifications subscriptions/destinations. Includes company isolation, encrypted credential references, bounded downloads, whole-record paging with cursors and offsets, per-operation token-bucket pacing from Amazon's published burst and rate, explicit `writes` declarations (only `amazon_request_report` is a write), host failure codes, per-tool execution timeouts, output projection, activity logging, and synthetic protocol tests. Ads and notification ingestion are excluded.

## Install and configure

1. Build from this repository using Node 22 or newer. From `plugins/amazon-tools`, run `pnpm install --frozen-lockfile` and `pnpm build`. The build uses the existing `vendor/sdk/*.tgz` packages; do not repack the SDK. Install the resulting plugin through Paperclip's ordinary Plugin Manager or local-plugin installer. Release packaging discovers this folder automatically.
2. Register a private SP-API application for your own seller account, request the roles below, then self-authorize it. Amazon eligibility and approval still apply. [Amazon's connection instructions](https://developer-docs.amazon/sp-api/docs/connecting-to-the-selling-partner-api) describe self-authorization and Login with Amazon (LWA) token exchange. LWA is Amazon's authorization service. SP-API does not require AWS IAM keys or Signature Version 4 signing.
3. On the **Secrets** page of each company that will use the connection, create a secret, for example named `AMAZON_SP_API_CREDENTIALS`. Its value must be JSON with exactly these four string fields:

   ```json
   {"clientId":"example-client-not-real","clientSecret":"example-secret-not-real","refreshToken":"example-refresh-not-real","sellerId":"SELLEREXAMPLE"}
   ```

   The plugin settings form cannot create secrets. Its **Encrypted LWA credentials JSON** field picks one of the company's existing secrets, or takes a pasted secret ID. Configuration retains only `credentialsRef`. The worker resolves that reference with the calling company through `ctx.secrets.resolve(ref, companyId)`. There is no plugin credential input/read-back action, raw-credential config field, or credential output tool. Never pass credential values as tool arguments.
4. In Configuration, add a unique connection key, pick the secret, choose `NA`, `EU` or `FE`, and add marketplace IDs served by that region. Select explicit allowed company IDs. Missing, empty, malformed, duplicate or wildcard company lists deny access. The selected secret must belong to the calling company. For multiple companies, use separate connection entries and company-owned secrets; a reference belonging to another company will fail resolution.
5. Save, then call `amazon_test_connection` from an allowed company's agent. Include `account` if that company has multiple configured connections, and `marketplaceId` if the connection has several marketplaces. This reads one listing and confirms that authorization path. It does not prove optional roles. Settings config validation checks structure only; worker health is not a live Amazon connection test.

The host's secret service stores the encrypted value. The SDK's `ctx.secrets.store` is available for plugin-owned generated material, but this plugin does not invent a second credential-entry UI or store credentials in plugin state. No saved secret values are returned by this plugin.

## Roles and prerequisites

Amazon's roles are broad permissions, not read-only credentials. Several roles also authorize writes outside this plugin. The plugin's fixed operation surface, rather than credential permissions, enforces its behavior. Request only the roles for enabled use cases. Do not request restricted roles: [Orders v2026-01-01](https://developer-docs.amazon/sp-api/docs/orders-api-migration-guide) gates buyer and recipient personal data by those roles alone, with no Restricted Data Token step, and this plugin never requests that data.

| Capability | Suitable non-restricted role / prerequisite |
| --- | --- |
| Transactions, balances, settlement reports | Finance and Accounting. |
| Orders | Finance and Accounting is sufficient for these reads; Inventory and Order Tracking or Amazon Fulfillment also qualifies. |
| FBA inventory and FBA inventory report | Amazon Fulfillment. |
| Merchant listing availability and open-listings report | Inventory and Order Tracking or Product Listing. |
| Catalog Items | Product Listing. |
| A+ document reads | Brand Analytics or Product Listing; account, brand and marketplace eligibility still applies. |
| Sales and traffic report | Brand Analytics; availability is subject to Amazon approval. |
| `ANY_OFFER_CHANGED` subscription inspection | Pricing. |
| `LISTINGS_ITEM_STATUS_CHANGE`, `LISTINGS_ITEM_ISSUES_CHANGE`, `BRANDED_ITEM_CONTENT_CHANGE` inspection | Product Listing. |
| Application destination inspection | No seller role; grantless `sellingpartnerapi::notifications` token from the configured app. |

Primary references: [operation role mappings](https://developer-docs.amazon/sp-api/docs/role-mappings), [report and notification role mappings](https://developer-docs.amazon/sp-api/docs/role-mappings-for-types), [A+ API guide](https://developer-docs.amazon/sp-api/lang-pt_BR/docs/a-plus-content-api-use-case-guide), and [Notifications auth/roles](https://developer-docs.amazon/sp-api/docs/notifications-api). Ask Amazon to approve the roles before expecting live data; this plugin cannot grant eligibility.

## Report generation is declared as a write

`amazon_request_report` is the only tool that changes anything outside Paperclip: it asks Amazon to create a report. Following Paperclip's plugin spec (sections 11.1 and 11.7), it is declared `writes: true` with no `actionType`, because none of the host's action categories fits. Every other tool is declared `writes: false`, so the host never guesses from a tool's name. What that means in practice:

- **Approval.** For an agent run, the host treats a write without an action category as "ask first", so each agent call is queued for a person to approve and runs once approved. The host's per-category action settings do not apply to it. Clippy chat calls, made by a person, are not held by this policy.
- **Repeat protection.** The host claims each call before running it. A repeat of the same call in the same run (or with the same scoped idempotency key) replays the first result instead of creating a second report. The current host does not check a settled result's expiry when replaying it, so this is not a reliable 30-minute retry window.
- **What the plugin returns.** Before the report POST is sent (invalid input, company or configuration denial, credential or sign-in failure, a rate wait that is too long, an unopened connection, or the deadline passing before sending), no report can have been created. A 4xx refusal, including 429, did reach Amazon but is assumed to mean no report was created. In both cases the failure is raised as an error so the host releases its claim and an identical retry may run. When the report POST may have taken effect, the failure is returned as a settled result: `EREPORT_UNKNOWN` (network error, 5xx, deadline or invalid reply after sending) or `EREPORT_DISPATCHED` (Amazon accepted it, but the connection's configuration or credentials changed before the result returned, so the report ID is withheld). Neither should be repeated blindly; call `amazon_list_reports` first.
- **Duplicate-report limits.** If Amazon created a report but still answered 4xx, releasing the claim would let a retry create a second read report. If the worker crashes or is stopped during the POST (upgrade, disable, uninstall or instance shutdown), the host sees an RPC error and releases its claim, with the same risk. Repeat protection cannot guarantee exactly one report at the external provider.
- Report creation is never retried automatically, including after a 429.

## Reports, settlements and payouts

The report allowlist is deliberately small:

- `GET_V2_SETTLEMENT_REPORT_DATA_FLAT_FILE_V2`: Amazon-generated TSV, discover/download only. Deposit dates and settlement totals provide payout reconciliation evidence. There is no fictitious list-settlements API. [Amazon's settlement report rules](https://developer-docs.amazon/sp-api/docs/report-type-values-settlement).
- `GET_FLAT_FILE_OPEN_LISTINGS_DATA`: requested merchant listing inventory/price summary. No buyer data. [Inventory report definition](https://developer-docs.amazon/sp-api/docs/report-type-values-inventory).
- `GET_FBA_MYI_UNSUPPRESSED_INVENTORY_DATA`: requested FBA inventory summary. [FBA report definitions](https://developer-docs.amazon/sp-api/docs/report-type-values-fba).
- `GET_SALES_AND_TRAFFIC_REPORT`: requested aggregate sales/traffic JSON. Requires `dataStartTime` within two years; the plugin limits the date range to at most 30 days, ending over two minutes ago. If `dataEndTime` is omitted, it uses the earlier of now minus three minutes and start plus 30 days, so approval delays do not make the window exceed the limit. Supply an explicit end for an exact window. Both inventory report types refuse start/end dates. The 30-day cap is the plugin's choice: [Amazon](https://developer-docs.amazon/sp-api/docs/report-type-values-analytics) recommends 7 to 30 days to reduce processing time and only requires the start to be within two years. The plugin fixes granularity to DAY and SKU. No arbitrary report options.

`get_report` first verifies the report type and marketplace scope, then obtains its document metadata internally. Only known columns or aggregate JSON fields are returned. No raw reports, pre-signed URLs, unrestricted text, order reports, tax reports or buyer details are exposed. TSV files with unknown/localized headers, duplicate headers, multiline values or rows with the wrong number of columns fail closed rather than guessing column positions. Quote characters inside a cell, such as an inch mark in a product name, are ordinary data. Decimal commas are preserved as strings.

Report documents are decoded with the charset their download declares in `Content-Type`, as in [Amazon's retrieve-a-report sample](https://developer-docs.amazon/sp-api/docs/retrieve-a-report). Supported labels are UTF-8, windows-1252 (including `Cp1252`) and Shift_JIS (including `windows-31j`); windows-1252 is decoded from the WHATWG table because Node's own decoder maps 0x80 to 0x9F as control characters. Any other label, or more than one charset parameter, fails with `EDOWNLOAD`. A download with no charset is decoded as strict UTF-8 only, so a non-UTF-8 document without a label fails rather than being guessed. Which charsets Amazon actually declares for each marketplace has not been verified against a live account.

Finances uses current transactions, not a legacy events endpoint. Date windows are limited to 180 days and must end over two minutes ago; results may lag 48 hours. `ORDER_ID` and `FINANCIAL_EVENT_GROUP_ID` are the supported identifier filters. The response may contain settlement/disbursement identifiers for reconciliation. By default, finance reads the authorized seller account across marketplaces, because Amazon explicitly warns that supplying `marketplaceId` excludes US merchant-fulfilled transactions. Specify a configured marketplace only when that restriction is intended. [Current transaction contract](https://developer-docs.amazon/sp-api/reference/listtransactions).

## Listing Watch and Notifications boundaries

For comparison, read the catalog ASIN with `amazon_get_catalog_item` and the seller SKU with `amazon_get_listing`. Catalog data represents Amazon's catalog view; Listings Items attributes represent the seller's latest submitted values, while fulfillment availability is live. These reads do not identify the author of an override or reproduce every rendered retail detail-page element. Selected title, bullets, description, brand and image fields are supported; arbitrary product-type contact/compliance attributes are excluded. [Amazon's explanation of submitted versus live listing data](https://developer-docs.amazon/sp-api/docs/listings-items-api).

A+ text comes from `TextComponent.value`, `PlainTextItem.value` and comparison product titles (`StandardComparisonProductBlock.title`), so standard comparison tables return their product titles, metric values and row labels. A+ list continuations send `pageToken` as the only query parameter, following the explicit pagination rule in the [searchContentDocuments](https://developer-docs.amazon/sp-api/reference/searchcontentdocuments) and [searchContentPublishRecords](https://developer-docs.amazon/sp-api/reference/searchcontentpublishrecords) references. The same references also mark `marketplaceId` as required, which contradicts that rule; live behavior has not been verified.

The four notification types above can be inspected only after an operator provisions destinations/subscriptions for the same application and seller through an approved external process. `ANY_OFFER_CHANGED` commonly uses SQS; the listing status/issues and branded-content events support EventBridge workflows. See [Amazon's EventBridge setup](https://developer-docs.amazon/sp-api/lang-en_EN/docs/set-up-notifications-with-amazon-eventbridge) and [Notifications guide](https://developer-docs.amazon/sp-api/docs/notifications-api). This plugin creates no AWS resources or subscriptions, makes no SQS receive/delete calls, and has no event consumer, webhook, scheduled poller, alerts or automatic Listing Watch workflow. Application destination inspection is app-wide, not a list of this seller's received events.

## Paging and continuation

- A response holds whole records only: at most `limit` records where the tool has `limit` (1 to 100, default 25), and at most 72 KiB and 1,400 projected nodes of records. A record that does not fit is never dropped; it stays reachable.
- List tools return `nextCursor` while anything remains. A cursor first serves the records of Amazon's page that were already fetched but not yet returned, then asks Amazon for the next page with the original filters (report and A+ lists send only Amazon's page token, as Amazon requires). Reuse the same arguments plus the cursor; a cursor can be retried, returns the same page each time, and is not used up by a failed call. Finance and Orders fix omitted end dates on the first call; later continuations use those validated absolute dates. Orders requires exactly one creation/update start and only its matching end, with a maximum 730-day window. `nextCursor: null` means the end. Empty pages with a cursor still require continuation.
- Cursors are random, memory-only handles tied to the operation, exact arguments, company, connection and current credentials. Each newly issued cursor expires after 15 minutes, on worker restart or configuration change, or when evicted (at most 500 cursors and 24 MiB of cached records per worker, oldest first). Continuing with fresh cursors keeps a chain alive beyond 15 minutes; reusing an old cursor does not extend that cursor's lifetime. An expired, evicted or foreign cursor returns `ECURSOR`; repeat the query without a cursor. Provider tokens have separate hard lifetimes only where Amazon documents one: [FBA inventory](https://github.com/amzn/selling-partner-api-models/blob/main/models/fba-inventory-api-model/fbaInventory.json) 30 seconds (the plugin uses 25 seconds for a safety margin), and [Orders](https://github.com/amzn/selling-partner-api-models/blob/main/models/orders-api-model/orders_2026-01-01.json) 24 hours. A cursor that needs the next provider page after that returns `EPAGE_EXPIRED` without sending the expired token; already fetched records remain readable within the local cursor lifetime. Other tokens have no invented hard expiry; Amazon can still reject an expired token. For a full FBA snapshot use the FBA inventory report, or narrow with `sku`.
- Cached records are the projected, secret-scrubbed output, never raw provider data, download URLs or buyer fields.
- Downloaded reports use row offsets: `nextOffset` counts the rows actually returned, and `null` means the end. For the sales and traffic report, `salesAndTrafficByDate` and `salesAndTrafficByAsin` page independently. With no offsets, both arrays start at 0; afterwards pass `dateOffset` and/or `asinOffset` for the arrays you still need, each from its `nextDateOffset` or `nextAsinOffset`. Naming only one array reads only that array. `offset` is accepted as a shorthand that starts both arrays at the same position and cannot be combined with the specific offsets.
- The projected rows of a DONE report are kept in memory for 15 minutes (at most 8 reports and 16 MiB per worker), bound to the company, connection, current credentials, tool and report ID, so later offsets do not download the document again. Configuration rechecks still run before every result. Rows of a very large document may not be cached; those pages download the document again.
- `amazon_get_aplus_content` returns whole modules per call and continues with `moduleOffset` and `nextModuleOffset`.
- `truncated: true` means a returned record had fields trimmed: a nested list over 100 entries, a string over 1,500 UTF-16 code units, more than 32 KiB of text in one record, or one record too large for a response on its own (it is projected again with fewer nodes). Text cuts preserve complete surrogate pairs (including emoji); NUL characters are removed and already unpaired surrogates are replaced with U+FFFD so projected text can be stored as PostgreSQL JSON. Text normalization also sets `truncated`. A+ returns up to 50 text items per module and reads at most 100 modules.

## Bounds, retries and privacy

- Company checks precede secret resolution and networking. The worker reloads config and rechecks the current company-owned secret before each network step and before returning results, including results served from memory. Credential/config changes invalidate authorization reuse. Tokens are cached only in memory, separated by company/config/credential digest and authorization grant; references are resolved afresh on every call. Config changes/shutdown clear tokens, cursors, cached report rows and pacing state.
- Every invoked tool attempts a fixed-metadata activity start and outcome entry, including failures. Entries contain operation, outcome, bounded result count and truncation flag, never arguments, credentials, seller details, provider response bodies or report URLs. An unavailable start audit prevents network access. A failed outcome entry is logged as a worker warning and does not turn a completed call into a failure. No external telemetry is used.
- Fixed LWA and regional API hosts only. No arbitrary URL, method, endpoint or authentication passthrough. Report downloads allow HTTPS S3 bucket/CloudFront host shapes only, verify and pin public IPv4 DNS addresses, validate TLS, reject redirects/embedded credentials/extra ports, and receive no Amazon access-token header. IPv6-only networks and other download host shapes are unsupported and fail closed.
- The transport runs inside the worker using Node HTTPS because the current SDK HTTP bridge drops redirect/abort controls and buffers response text. Each request has an 8 MiB byte cap and ends at 20 seconds or the call's total deadline, whichever is first; gzip expansion is also capped at 8 MiB. No raw document is saved to disk. [Amazon's report retrieval workflow](https://developer-docs.amazon/sp-api/docs/retrieve-a-report).
- Each tool declares `executionTimeoutMs`: 120 seconds for `amazon_get_report` and `amazon_get_settlement`, 70 seconds for the rest. The worker ends its own work, including host lookups and rate waits, 20 seconds before that, so the host never gives up on a call that is still running. A read that reaches the deadline returns `EDEADLINE`; a report request interrupted after sending returns `EREPORT_UNKNOWN`.
- Pacing is a token bucket per seller, application and operation, seeded with Amazon's published burst and refilled at the published rate (for example `searchOrders` 20 calls then 0.0056 per second, `getReportDocument` 15 then 0.0167 per second). `x-amzn-RateLimit-Limit` replaces the rate for that seller, application and operation only; zero, negative or malformed values are ignored. GETs retry only HTTP 429, at most three attempts, waiting for `Retry-After` or an exponential backoff. A required wait over ten seconds, or one that would cross the deadline, returns `ERATE` with seconds to wait instead of sleeping. Independent worker processes still share Amazon's upstream limits; pacing is local to one worker.
- Failures carry Paperclip's failure codes, so agents get the right next step: `invalid_input` (bad arguments, `ECURSOR`, `EPAGE_EXPIRED`), `not_authorized` (company, configuration or report scope), `needs_reconnect` (credentials or Amazon authorization), `unavailable` (network, `ERATE` with `retryAfterMs`, activity log), `timeout` (`EDEADLINE`), `not_found` (HTTP 404) and `failed` (everything else, including `EREPORT_UNKNOWN` and `EREPORT_DISPATCHED`).
- Amazon sign-in network failures, 429 and 5xx are transient failures, not a request to reconnect. A 429 carries a sanitized `Retry-After` hint; only HTTP 400/401 or a malformed token grant means `EAUTH`. Host configuration/secret lookup trouble returns sanitized `EHOST` (`unavailable`); missing/foreign secret references and malformed credentials remain `ECREDENTIALS`, while company/configuration denial stays permanent. Oversized plain or gzip responses keep `ERESPONSE` (`failed`, not retryable), rather than inviting another download.

## Deliberately excluded data

These fields are left out on purpose, to keep free-form provider text, payment details and buyer data out of agent context. Adding any of them is a scope decision, not a bug fix:

- Listing issue `message` text (codes, severity, attribute names and categories are returned).
- Transaction `description` and every transaction `contexts` entry, including product, deferral and payment/bank contexts (so deferral reasons and maturity dates are not returned).
- Order buyer, recipient, tax, payment, gift and customization data, even if Amazon returns it.
- The configured seller ID and every credential value are replaced by `[redacted]` wherever they appear in returned data, even inside other values, such as a SKU that contains the seller ID. Selected strings are scrubbed before normalization and text cuts, then again after normalization and projection; unselected raw objects are never recursively copied for redaction.

## Verification

From `plugins/amazon-tools`:

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
pnpm test:runtime
```

The tests use synthetic credentials and data only. `src/amazon.test.ts` covers mappings, isolation, credentials, redaction, downloads, TSV and charset handling; `src/continuation.test.ts` covers whole-record paging, cursors, cached remainders and A+ modules; `src/limits.test.ts` covers pacing, deadlines and report-request outcomes; `src/worker.test.ts` covers the tool registry, write declarations, failure codes and claim release. The runtime test copies only built install artifacts into an isolated scratch directory under the checkout's ignored `.smoke-tests/`, validates the manifest with the vendored host schema, checks the built `writes` and timeout declarations, launches the actual bundled worker, exercises JSON-RPC initialization/config validation/tool execution/cursor continuation/report-request outcomes/config revocation, and sends the worker's real HTTP request construction through a loopback fake Amazon server. It does not install into a live/global plugin root or contact Amazon. The test adapter is outside `dist/` and cannot change production endpoints.

Runtime cases also cover sign-in failure classification and 9 MiB plain/API responses plus oversized gzip expansion through the real transport. To include the isolated PostgreSQL JSON roundtrip, set `AMAZON_TEST_PGLITE_MODULE` to an already installed PGlite module file before `pnpm test:runtime`. This optional test uses an in-memory database, rejects the original NUL/unpaired-surrogate examples, then roundtrips the worker's projected output; it adds no runtime dependency.

Live seller acceptance remains an operator step: approve roles, create the secret, pick it in the settings form, run the connection test, then call the relevant tools with real report/order/ASIN/SKU IDs. Live credentials, eligibility, account-specific schemas, Amazon's real page sizes and charsets, and secret UI masking have not been verified against a running Paperclip instance or a real seller account. Amazon Ads remains phase 2 with separate authentication.
